# RADAR 0.1 — Design

Date: 2026-11-17
Status: Draft for approval
Sources: `_dev/PRD.md`, `_dev/PRD_implementation_direction.md`, `_dev/RADAR_Technicals.md`, and the design conversation of 2026-11-17.

---

## 1. Intent

`radar` is a Rust crate that simulates radar sensors for games and synthetic environments. Today most games treat radar as "everything within R is revealed". This crate replaces that with what a real radar knows: noisy, sometimes missing, sometimes false measurements, with anonymous tracks built up from them over time.

The crate has to be useful to many different host crates, not just one game. It should be realistic enough to simulate real scenarios to a credible degree, but simple and cheap enough for games. Generality and realism are both goals. A thin 2D "detection radius" crate would not be worth publishing.

The first host is the author's own pure-Rust `robocode` crate (`/Users/cp/wer/crt/robocode`, v0.5.0). robocode gets a `ScanModel` seam, keeps its classic exact scan as the default, and gains a realistic scan backed by `radar`.

## 2. Goals, non-goals, anti-goals

### Goals (0.1)
- Native 2D and 3D sensing on one 3D core.
- The host controls time; scheduling is deterministic; each sensor has its own update rate; large steps are subdivided.
- The host supplies world snapshots and never hands over ownership of ground truth.
- Radar sensors with scan patterns (fixed, circular, sector, raster, volume, host-steered) and beam geometry.
- Detection driven by the radar range equation and signal-to-noise ratio (SNR), with target fluctuation (Swerling), false alarms, missed detections, and measurement noise that scales with SNR. There is also a cheap "radius" detection model behind the same interface.
- Line-of-sight occlusion through a host-provided environment trait.
- Tracking: gated nearest-neighbour association, alpha-beta and linear Kalman filters, track lifecycle, prediction, and covariance output.
- Anonymous track IDs, plus optional cooperative identification (IFF-style transponder codes).
- An electronic-warfare foundation: an emitter list in the world snapshot, noise jamming that raises the receiver noise floor, and jamming-strobe observations.
- Seeded deterministic randomness, with optional OS/hardware entropy seeding (the seed used is recorded) and a pluggable `RandomSource`.
- robocode integration: the `ScanModel` seam, the classic model (identical to today's behaviour), and a realistic model backed by `radar`.

### Non-goals (0.1)
- Waveform-level signal simulation and specific technologies (pulse, CW, FMCW, phased array, SAR, MIMO). These are later releases; nothing in 0.1 should be named after them.
- Passive ESM sensors, deception jamming, chaff, decoys.
- Clutter, atmospheric attenuation, multipath (0.1 only leaves room for them in the `Environment` trait).
- Multi-sensor fusion (each sensor has its own tracker in 0.1).
- C ABI, Java, Python bindings. Parallel execution. `no_std`.
- A visual viewer or scenario editor.

### Anti-goals (a failure even if it "works")
- **Ground truth leaking through the normal API.** `Measurement` and `Track` never carry a `TargetId`, and false alarms are indistinguishable from real returns. Truth is available only through an opt-in diagnostics feature.
- **Game-specific data in `radar`.** Opponent energy, names, or "true heading" never appear in `radar` types. Those are host extras (robocode's adapter adds them).
- **Non-reproducible runs by default.** The same seed, config, inputs and step sequence must give identical observation streams.
- **Breaking robocode's classic behaviour.** With the default scan model, robocode's parity output must be byte-identical to today's.
- **Configuration that does nothing.** Don't expose options whose models don't exist yet.

## 3. Constraints

- Licence: AGPL-3.0-only (author's decision; see §13 open item on robocode's EPL-1.0).
- Rust edition 2024, `rust-version = "1.85"`.
- One crate with modules behind feature flags (ADR-010). No workspace split yet.
- A small runtime dependency set: `rand_core` + `rand_chacha` (seeded streams), `thiserror`; optional `serde`, `getrandom`/OS RNG (via an `entropy` feature). No `glam` or `nalgebra`; RADAR owns its geometry types and does its own small fixed-size matrix maths. The builder pins exact versions against crates.io at bootstrap.
- Single-threaded, deterministic core.
- No panics for user input; config validated at `build()` with typed `RadarError`s.
- Everything internal is in SI units and radians; degree helpers are offered at the API edge.

## 4. Approaches considered

**Model composition** (how a radar is assembled from scan / detection / noise / tracker stages):

| | Approach | Trade-off |
|---|---|---|
| **A (chosen)** | Built-in models as config **enums**, each stage with a `Custom(Box<dyn Trait>)` escape hatch | Configs are plain data: serializable, FFI-friendly later, one sensor type in a `Simulation`. Cost: enum dispatch per stage, and `Custom` variants are not serializable. |
| B | Fully generic `Radar<S, P, D, M, T>` | Fastest (monomorphised), but unwieldy types, heterogeneous sensors need boxing anyway, and serde/FFI become hard. |
| C | Every stage a trait object | Most uniform, but configs aren't serializable without extra machinery, and simple setups get wordier. |

The author chose **A** because it serves game devs (a few lines of config), simulation users (saveable, replayable scenarios) and extenders (trait hatch). It matches Technicals ADR-005.

**Crate layout:** single crate with feature-gated modules (chosen) vs. an immediate multi-crate workspace (rejected: versioning overhead before the boundaries are proven).

**robocode integration:** a `ScanModel` trait seam inside the robocode engine (chosen) vs. a wrapper that rewrites `TurnEvents` after the classic scan (rejected: the classic scan has already leaked ground truth by then).

**Noise source:** seeded ChaCha streams by default (chosen). Hardware entropy as the sampling source was considered and rejected as a default because it breaks replay and adds no statistical realism. It is available as a seed source (recorded) and through a `RandomSource` plug-in, explicitly marked non-deterministic.

## 5. Decisions taken with the author

1. Scope is the full Technicals 0.1 (option C), including tracking, 3D, scheduling, subdivision and interference.
2. Composition approach A; single crate, feature-gated modules.
3. robocode integrates through a `ScanModel` trait seam, not a wrapper.
4. robocode wraps radar. Energy and true-heading "reads" are optional robocode game rules, not radar features.
5. Realism comes first in `radar`: observations contain only physically measurable quantities. Heading and speed come from track estimates (and Doppler radial velocity), not reads.
6. Targets are anonymous: tracks have anonymous `TrackId`s. Identity is available only through optional cooperative identification.
7. AGPL-3.0-only, edition 2024.

### 6.1 Module layout and features

### 6.2 Conventions (document in rustdoc and an ADR-style section of the README)
- World frame: right-handed, **x = east, y = north, z = up**. Metres, seconds, radians, hertz, watts, square metres.
- **Azimuth** is the compass bearing: measured from +y (north), **clockwise**, in `[0, 2π)`. **Elevation** is measured up from the horizontal plane, in `[-π/2, π/2]`. This matches robocode's heading convention (0 = north, clockwise).
- Platform and sensor frames are defined by `Pose3`. A sensor's mount orientation is relative to its platform.
- `WorldScale { metres_per_unit, seconds_per_tick }` (default 1.0 / 1.0) is a small helper for hosts. It converts host positions, velocities, durations and angles-per-tick to and from SI at the boundary. The core never sees host units.
- 2D is `z = 0` with elevation ignored. A sensor's `Dimension::TwoD` skips elevation measurement and elevation beam limits; it is not a separate engine.

### 6.3 Time
- `SimTime(u64 ns)` and `SimDuration(u64 ns)` with `from_secs_f64`, `from_millis`, etc. These are integer ticks, with no accumulated float drift (584-year range).
- `StepPolicy::{SingleStep, Subdivide { max_step }}`. `step(dt)` splits `dt` into sub-steps no longer than `max_step`.

### 6.4 World input
```rust

    pub time: SimTime,
    pub platforms: Vec<PlatformState>,
    pub targets: Vec<TargetState>,
    pub emitters: Vec<EmitterState>,   // empty unless EW used
}
pub struct PlatformState { pub id: PlatformId, pub pose: Pose3, pub velocity: Vector3 }
pub struct TargetState {
    pub id: TargetId,
    pub pose: Pose3,
    pub velocity: Vector3,

    pub transponder: Option<TransponderCode>,

```
- `Simulation::update_world(snapshot)` replaces the current snapshot (it is validated: finite values, unique IDs, `rcs_m2 >= 0`). Targets are processed in ascending `TargetId` order, whatever order the snapshot is in.
- Within sub-steps between snapshots, target and platform positions are **linearly extrapolated** from snapshot time using their velocities.
- `RadarSignature` is a struct now; aspect- and frequency-dependent signatures are a later extension through a `SignatureModel` trait. Leave room, but don't build it.

## 7. Sensor and radar model

### 7.1 Sensor framework
```rust
pub trait SensorModel: Send {
    fn update(&mut self, ctx: &SensorContext, out: &mut Vec<Observation>) -> Result<(), RadarError>;
}
```
`SensorContext` gives the current time, the update interval, the sensor's platform pose, the extrapolated world view, the environment, and the sensor's `RandomSource`. The registry stores `SensorEntry { id, platform, mount: Pose3, update_period, next_due, enabled, model: SensorKind }` where `SensorKind::{Radar(RadarSensor), Custom(Box<dyn SensorModel>)}`.

Scheduling rule: within each sub-step, every sensor whose `next_due <= t` updates, in ascending `SensorId` order. `next_due += update_period` (no drift). A sensor that missed several periods inside one sub-step updates once per missed period, each at its own due time.

### 7.2 RadarConfig (approach A)
```rust
pub struct RadarConfig {
    pub dimension: Dimension,                 // TwoD | ThreeD
    pub update_period: SimDuration,
    pub antenna: AntennaConfig,               // beamwidth_az, beamwidth_el, pattern: Gaussian | Uniform
    pub scan: ScanConfig,
    pub detection: DetectionConfig,
    pub measurement: MeasurementConfig,
    pub limits: RangeLimits,                  // min_range, instrumented_range
    pub doppler: bool,                        // measure radial velocity
    pub identification: Option<IdentificationConfig>,
    #[cfg(feature = "tracking")]
    pub tracker: TrackerConfig,
    #[cfg(feature = "ew")]
    pub receiver_band: Option<Band>,          // centre frequency + bandwidth, for jamming overlap
}
```
Built with `RadarConfig::builder()...build() -> Result<RadarConfig, RadarError>`. Presets:
- `RadarConfig::simple_2d(range_m)`: circular scan, radius detection, no noise. This is the "arcade" game entry point.
- `RadarConfig::surveillance_2d()` / `surveillance_3d()`: range-equation detection with sensible defaults.

### 7.3 Scan patterns
`ScanConfig::{Fixed{az, el}, Circular{rate, el}, Sector{centre, width, rate}, Raster{az_span, el_span, rows, rate}, Volume{el_bars: Vec<f64>, rate}, Steered{max_slew_rate}, Custom(Box<dyn ScanPattern>)}`.
- Each update the scan produces a **swept arc**: the beam's boresight at the start and end of the interval. A target is illuminated if its angular extent (`asin(extent_radius / range)`, clamped) plus half a beamwidth overlaps the arc. This generalises robocode's arc test.
- Each target gets at most one look per update. `build()` rejects a config whose swept angle per update can exceed 360° (scan rate × update period); the user must shorten the period instead. *(Builder's call, recorded here.)* If range < extent radius, the target's angular half-extent is π (always overlaps), as in robocode.
- `Steered`: the host commands `Simulation::command_beam(sensor, az, el)`; the beam slews toward it, capped at `max_slew_rate`. robocode, turrets and phased arrays all use this.
- Beam pointing is relative to the sensor mount, which is relative to the platform pose. Platform rotation therefore drags the beam unless the scan compensates. The builder chooses whether scan angles are platform-relative (default) or world-stabilised (a flag); both are needed.

### 7.4 Detection
`DetectionConfig::{Radius{range, pd}, RangeEquation(RangeEquationConfig), Custom(Box<dyn DetectionModel>)}`.

**Radius:** illuminated, in range and with line of sight → detected with probability `pd`. No SNR; measurement noise comes from fixed sigmas only.

**RangeEquation:** single-look, square-law, monostatic.
- SNR: `SNR = K · σ · g(θ)² / (R⁴ · L)`. Here `g` is the normalised antenna pattern gain at the off-boresight angle (Gaussian or uniform), σ is the fluctuated RCS for this look, and `L` is the system losses. `K` comes from one of two calibrations:
  - **Physical:** `peak_power_w, gain_db, frequency_hz, noise_figure_db, bandwidth_hz, losses_db` give `K = Pt G² λ² / ((4π)³ k T0 F B)`.
  - **Reference (game-friendly):** "a σ_ref target at R_ref gives SNR_ref dB", so `K = SNR_ref · R_ref⁴ / σ_ref`. A helper derives SNR_ref from "Pd = 0.9 at Pfa = 1e-6".
- Fluctuation per look: Swerling 0 uses σ as is; Swerling 1 uses `σ · Exp(1)`; Swerling 3 uses `σ · Gamma(2, 1/2)`.
- **Decision by sampling the envelope**, not by a Pd lookup: draw complex Gaussian noise `n` (unit power), form `|√SNR + n|²`, and compare it with the threshold `T = −ln(Pfa)`. This is exact for square-law detection, makes false alarms and detections consistent, and yields a *measured* SNR for noise scaling.
- Pd is computed analytically **only for diagnostics** (Swerling 1 closed form `Pfa^(1/(1+SNR))`; the Swerling 0 method, North's approximation or Marcum-Q, is the builder's choice).
- Jamming (feature `ew`) adds `J/N` to the noise term: `SNR = S / (N + J)`.
- Line of sight is checked through `Environment` before detection. An occluded target produces nothing.

### 7.5 False alarms
For each update, the number of resolution cells looked at is `cells = (instrumented_range / range_resolution) × max(1, swept_az / beamwidth_az) × (el factor in 3D)`. The false-alarm count is drawn as **Poisson(Pfa · cells)**, with positions uniform over the cells. They are emitted as ordinary `Measurement`s with SNR drawn from the noise-only tail above the threshold. The radius model has no false alarms unless it is given an explicit `false_alarm_rate` per scan.

### 7.6 Measurements
```rust
pub struct Measurement {
    pub sensor: SensorId,
    pub time: SimTime,
    pub range: f64,
    pub azimuth: f64,                 // world-frame compass bearing
    pub elevation: Option<f64>,       // None in TwoD
    pub radial_velocity: Option<f64>, // Some if doppler
    pub snr_db: Option<f64>,          // measured, None for Radius
    pub sigma: MeasurementSigma,      // range, az, el, rv standard deviations used
    pub identity: Option<TransponderCode>,
    pub sensor_position: Vector3,     // where it was measured from (needed for track conversion)
}
```
There is no `TargetId`. Noise: `MeasurementConfig::{Fixed{σr, σaz, σel, σrv}, SnrScaled{range_resolution, rv_resolution, floor}}`. With `SnrScaled`, `σr = range_resolution / √(2·SNR)` and `σangle = beamwidth / (1.6·√(2·SNR))`, each floored. Radial velocity is the true relative velocity projected on the line of sight, plus noise.

### 7.7 Identification (optional, cooperative)
`IdentificationConfig { reply_probability, max_range }`. When a target with a `transponder` is detected and within `max_range`, it replies with `reply_probability` (seeded), and the code is attached to that `Measurement`. Targets without transponders never identify. This models a secondary radar co-mounted with the primary one. Tracks adopt the code most frequently seen on their associated measurements.

## 8. Tracking (feature `tracking`)

- One tracker per radar sensor in 0.1 (fusion comes later). `TrackerConfig::{None, AlphaBeta{alpha, beta}, Kalman{process_accel_sigma}, Custom(Box<dyn Tracker>)}`.
- **State:** constant velocity, `[x y z vx vy vz]`, in the world frame. 2D sensors keep z and vz at zero with tiny variance.
- **Measurement conversion:** polar to Cartesian using `sensor_position`, with converted covariance (first-order Jacobian). Doppler radial velocity is used as an additional scalar update when present (EKF-style, linearised at the predicted state). The builder may defer the radial-velocity update to after the position update works, but it is in 0.1 scope.
- **Association (amended during implementation):** each update, tracks are predicted to the measurement time. Measurements are sorted by (range, azimuth) and gated by Mahalanobis distance (χ² gate, default 99%). Assignment is greedy and **two-pass, track-priority**: established tracks (Confirmed, Coasting) take measurements first, then Tentative tracks take what is left; within each pass pairs go nearest-first by d², ties broken by `TrackId` then measurement index. (A stale tentative's wide covariance gives it a small d², so it must not compete with established tracks.) Unassigned measurements start tentative tracks.
- **Dwells (amended during implementation):** for sweeping scans (Circular, Sector, Raster, Volume), a track's consecutive updates in the beam (plain illumination of its predicted position) form one dwell with at most one outcome, like a plot extractor: the first associated measurement updates the filter and records a hit; later measurements gated to the track in the same dwell are absorbed (no filter update, no new track). A dwell ends when the track leaves the beam or π has been swept since it started. For Fixed, Steered and Custom scans every update is its own dwell.
- **Lifecycle (amended during implementation):** `TrackStatus::{Tentative, Confirmed, Coasting, Deleted}`. Confirmation is M-of-N (default 3 of 5) over dwell outcomes. A track becomes Coasting after a dwell that ends in a miss.
  - **Confident-coverage miss counting:** a dwell without a hit is a miss only if, at some update in it, the track was *confidently* illuminated: its predicted direction lies inside the beam by its own angular uncertainty, margin `min(σ_ang, ½·half-beamwidth)` per axis with `σ_ang = position_sigma / max(range, 1 m)`. A dwell that only grazed the track records no outcome; a track outside the beam is never penalised.
  - **Deletion:** after `max_coast` consecutive misses (default 5); for Confirmed/Coasting tracks when the position sigma exceeds `max_position_sigma` (default `instrumented_range / 10`); for any track with a non-finite covariance.
  - **Tentative age-out:** a Tentative track is deleted once the time since its last hit exceeds `tentative_max_age` (default `(confirm_n + 1) ×` the scan's nominal revisit: one turn for Circular, all bars for Volume, out and back for Sector/Raster, a full circle at `max_slew_rate` for Steered, `update_period` for Fixed/Custom).
  - **Early deletion:** a Tentative track is deleted as soon as it can no longer reach M hits within its first N outcomes (`hits + (N − outcomes) < M`).
- **Output:**
```rust
pub struct Track {
    pub id: TrackId,                 // anonymous, monotonically assigned per sensor
    pub sensor: SensorId,
    pub status: TrackStatus,
    pub position: Vector3,
    pub velocity: Vector3,
    pub covariance: Covariance6,     // RADAR-owned 6×6 symmetric type
    pub identity: Option<TransponderCode>,
    pub first_seen: SimTime,
    pub last_update: SimTime,
    pub hits: u32,
    pub consecutive_misses: u32,
}
impl Track { pub fn predict(&self, at: SimTime) -> Track; pub fn course(&self) -> f64; pub fn speed(&self) -> f64; }
```
- Alpha-beta has no covariance of its own. It reports a covariance derived from the measurement sigmas and the alpha/beta steady state, documented as approximate.

## 9. Electronic warfare (feature `ew`)

```rust
pub struct EmitterState { pub id: EmitterId, pub platform: Option<PlatformId>, pub position: Vector3,
                          pub velocity: Vector3,
                          pub band: Band, pub erp_w: f64, pub kind: EmitterKind } // EmitterKind::NoiseJammer
```
- *Amendment (final fix wave):* `EmitterState` carries a `velocity`; the emitter position is extrapolated linearly to each sensor update (like targets and platforms) before strobe bearing, line of sight and J/N geometry are computed.
- Jamming power into a radar is `J = ERP · g_rx(θ_j)² … · λ² / ((4π)² R_j²) · overlap(band, receiver_band)`. Express it as `J/N` using the same calibration as §7.4. It adds to the noise term for every target evaluated in that update.
- A jammer whose J/N exceeds a configurable threshold while inside the beam produces an `Observation::JammingStrobe { sensor, time, azimuth, elevation, j_over_n_db }`. This is bearing only, with no range, as in real radar.
- Line of sight applies to jammers too.
- Radars do not yet register themselves as emitters (that comes with passive ESM later). The builder should keep `EmitterState` general enough for it.

## 10. Simulation API and outputs

```rust
let mut sim = Simulation::new(SimulationConfig::default().seed(Seed(12345)));
let s = sim.add_radar(SensorId(1), PlatformId(1), Pose3::IDENTITY, RadarConfig::simple_2d(1200.0))?;
sim.update_world(snapshot)?;
sim.step(SimDuration::from_millis(100), &OpenSky)?;
sim.drain(SensorId(1), &mut buf);        // Vec<Observation>, reusable buffer
for t in sim.tracks(SensorId(1)) { … }    // current tracks, snapshot copies
```
- `Observation::{Measurement(Measurement), TrackUpdated(Track), TrackDeleted{sensor, id, time}, ScanCompleted{sensor, time}, JammingStrobe{..}}`. Observations are ordered by time, then `SensorId`, then emission order.
- Other methods: `remove_sensor`, `set_enabled`, `command_beam`, `sensor_state(id)` (public runtime state: beam pointing, next due), `reset()`, `seed()`.
- `diagnostics` feature: `sim.drain_diagnostics(&mut Vec<DiagnosticRecord>)` gives per evaluated (sensor, target) pair the true range, SNR, analytic Pd, the outcome (detected / missed / occluded / out of beam), and for each measurement whether it was a false alarm or which `TargetId` caused it. This channel is separate from `Observation`.

## 11. Randomness and determinism

- `pub trait RandomSource { fn next_u64(&mut self) -> u64; }`. RADAR implements its own samplers on top of it (uniform via 53-bit mantissa, normal via Box–Muller or polar method, exponential, Poisson via inversion for small λ and PTRS or a normal approximation above a threshold). These are **implemented in-crate**, so stream outputs do not change when a dependency's sampling algorithm changes.
- Default: `rand_chacha::ChaCha8Rng` seeded from the simulation seed, with a **stream per sensor** using `set_stream(sensor_id)` plus a stream-version constant. Adding a sensor or a false alarm on sensor 1 never shifts sensor 2's randomness.
- Within a sensor, draws happen in a fixed order: targets in ascending `TargetId`, then false alarms, then identification replies, then tracking.
- `Seed::from_entropy()` (feature `entropy`) seeds from the OS/hardware RNG. `Simulation::seed()` returns the seed used, so the run can be replayed.
- `SimulationConfig::random_source_factory(Box<dyn Fn(StreamId) -> Box<dyn RandomSource>>)` lets a user drive sampling from live hardware noise. This mode is documented as **non-deterministic**.
- Documented limits: determinism holds for the same binary on the same target platform. Transcendental functions (`sin`, `cos`, `ln`, `exp`) can differ across platforms and libm versions. Cross-platform bit-exactness is not promised in 0.1.

### 12.2 Realistic scan (robocode feature `radar`, optional dependency on `radar`)
- `RadarScan` owns a `radar::Simulation`. At battle start it registers one sensor per robot (`SensorId = PlatformId = robot id`) with a robocode preset:
  - **Units:** a configurable `radar::WorldScale`, default 1 px = 1 m and 1 turn = 1 s (so 8 px/turn is 8 m/s). robocode's **built-in preset is calibrated in game units** (pixels, turns) and converted through the scale, so default gameplay feels the same at any scale. A user-supplied `RadarConfig` is in metres/seconds, so a real radar spec stays physically fixed while the arena's real size changes. robocode's frame is **y-down** (verified: `geometry.rs:89` computes bearings as `atan2(dx, -dy)`, so heading 0 points toward −y). The adapter maps `radar.y = -robocode.y` (x unchanged). Robocode headings and bearings in degrees are then compass bearings and convert directly to RADAR azimuth (degrees → radians, no offset). Velocity vectors follow the same flip.
  - Scan `Steered { max_slew_rate: 45°/s }`. Each turn the adapter calls `command_beam` with the robot's `radar_heading`. The swept arc is therefore exactly robocode's `last_radar_heading → radar_heading`.
  - Antenna beamwidth 3° (Gaussian), 2D, update period 1 turn.
  - Detection `RangeEquation` with reference calibration: robot σ = 1 m², Swerling 1, Pd 0.9 at 1000 m, Pfa 1e-6; instrumented range 1200 m.
  - Measurement `SnrScaled`, Doppler on, `Kalman` tracker, no identification by default.
- Each turn: build a `WorldSnapshot` from living robots (target extent radius = robot radius, `platform` = self so robots never see themselves), step 1 s with an `Environment` impl that does segment–rectangle intersection against `terrain.buildings`, and drain observations.
- `TurnEvents` gains `radar_tracks: Vec<RadarTrackReport>` (per scanner), filled only by `RadarScan`; `scans` stays empty in realistic mode. When a robot dies, its sensor is disabled and it is left out of later snapshots, so other robots' tracks on it coast and then are deleted naturally. *(My calls.)*
- **New robot-facing event** (realistic mode only): `Event::RadarTrack(RadarTrackEvent { track_id, status, bearing, absolute_bearing, distance, heading_estimate, velocity_estimate, position_sigma, identity: Option<String>, energy: Option<f64>, true_heading: Option<f64> })`, plus `Event::RadarTrackLost { track_id }`. These come with a default no-op method on the `Robot` trait. `ScannedRobotEvent` is **not** emitted in realistic mode.
- **Game rules** `RadarRules { identify_robots: bool, reveal_energy: bool, reveal_true_heading: bool }`, all default `false`. With `identify_robots`, every robot gets a transponder and the radar gets identification with reply probability 1.0, so identity resolves to the robot's name. `reveal_*` fill the optional fields from ground truth. These are explicitly game extras, injected by robocode, not `radar`.
- Strategy layer (`Observation.target`, fixed-point): in realistic mode, fill `TargetInfo` from the confirmed track nearest the robot, with `age` = turns since the track's last update. When `reveal_energy` is false, `TargetInfo.energy` must still hold a value. The builder picks a conservative convention and documents it (see §13).
- Recording/snapshot JSON: realistic-mode tracks are added to the turn snapshot under a new key. Existing keys are unchanged.

## 13. Open points for the builder (calls marked)

- **Builder:** exact dependency versions; the matrix implementation (const-generic or hand-written 6×6); the Swerling-0 analytic Pd method; the Poisson sampler threshold; module-internal naming.
- **Builder:** whether scan angles default to platform-relative or world-stabilised (both must be supported).
- **Builder (robocode):** the `TargetInfo.energy` value when energy is hidden. Suggested: the last revealed value if any, else the starting energy, documented.
- **Deferred by the author (licence):** robocode is EPL-1.0 and `radar` is AGPL-3.0-only, which may conflict when the `radar` feature is distributed. The author has put this aside for now; it does not block 0.1 work.

## 14. Acceptance criteria for 0.1

Through the public API only:
1. **Scenario A — 2D rotating radar:** one circular-scan radar, several moving targets of different RCS. Detection rate falls with range and RCS; misses and false alarms occur; tracks form, coast through misses, and estimate course within tolerance.
2. **Scenario B — 3D airborne surveillance:** a radar on a moving platform with volume scan, targets at different altitudes. Elevation is measured; 3D tracks are correct.
3. **Scenario C — multiple sensors:** two radars with different update periods. Their scan states, random streams and histories are independent. Adding a third sensor does not change the first two radars' outputs.
4. **Occlusion:** a target behind an `Environment` blocker is never detected.
5. **Jamming:** a noise jammer lowers detection probability along its bearing and produces strobes.
6. **Identification:** transponder targets get identity on tracks; others never do.
7. **Determinism:** two runs with the same seed and inputs produce identical `Observation` streams (compared exactly). Different seeds produce different streams.
8. **No truth leakage:** a test (compile-time or reflection-free API review) confirms that no public observation type contains `TargetId`.
9. **Statistics:** Monte-Carlo tests confirm that the sampled detection rate matches analytic Pd (Swerling 0/1) and that the empirical false-alarm rate matches Pfa, within confidence bounds.
10. **Property tests:** angle wraparound, frame transforms round-trip, time arithmetic, config validation.
11. **robocode:** parity output is unchanged with `ClassicScan`. A realistic-mode battle (open arena and urban map) runs to completion, robots receive only track events, buildings block detection, and the same seed replays identically.
12. **Bench:** a criterion benchmark for a 2D radar against 1,000 targets, with results recorded (target ≥ 60 updates/s, not a gate).
13. `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test --all-features`, and rustdoc on all public items, including each model's assumptions and limitations.
